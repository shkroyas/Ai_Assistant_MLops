# Live evaluation runtime

Qwen remains the fixed agent model for v1–v4. Following the user's authorization to use Qwen/Groq to complete execution, the independent judge is Groq GPT-OSS-20B. Gemini remains configured as an alternative, with its observed 5 RPM limit respected. Set JUDGE_PROVIDER=groq, JUDGE_MODEL=openai/gpt-oss-20b, JUDGE_API_KEY to the active local Groq key, and JUDGE_REQUEST_INTERVAL_SECONDS=10. Native Evidently LLMEval uses a registered LiteLLM wrapper with low reasoning effort and a 512-token completion ceiling.

The scratch harness admits at most four concurrent queries. Every completed sample is checkpointed before the next stage. Resuming preserves actual outputs and token usage; it does not synthesize repetitions. Checkpoint identity covers cases, repeats, configuration, prompt, advertised tool schemas, model and endpoint. Changed inputs reject stale checkpoints. Partial runs are explicitly tagged and marked KILLED in MLflow when stopped.

Identical native judge inputs share a cached verdict. Cache identity includes model, full judge messages (criteria, query, reference, response), and generation settings. Cached text is parsed using the current native descriptor parser. Changed criteria or answers require new requests. Agent samples remain independent. The synchronous native descriptor adapter is tested, not just an asynchronous helper. Calibration reuse additionally checks labels, approved review, provider/model and implementation identity. Native reports include every original row and its resolved verdict. The local judge cache is git-ignored; a clean clone makes fresh calls.

Without an explicit quota pool, Groq reserve keys can fail over only following authentication rejection (401/403), only for api.groq.com, and only without proxy cookies. HTTP 429 retains the current key and respects numeric Retry-After with bounded backoff. Shared account/project quotas are not bypassed. Primary Jupyter credentials remain separate from Groq credentials. Native SDK errors suppress credential-bearing exception chains.

Run stages with the README experiment commands. Re-running the exact command resumes completed samples. For an intentional fresh repetition, use a new version or archive the old evaluation directory first; do not silently delete evidence. Judge calls are paced and may take several minutes. Full metrics, gate decisions and report artifacts are recorded only after the stage genuinely completes. An evaluation-only run has no judge metrics and cannot be promoted.

## Explicit quota pool for the stronger candidate

The v13 Groq Qwen3.8-27B run was interrupted after its active bucket hit a real 200,000-token daily limit. It remains KILLED with all partial samples and infrastructure failures preserved. A one-call check of each supplied reserve key accepted the same input while the active key remained daily-limited (reports/groq_key_scope_checks.json). Additional keys were not assumed to provide quota before that check.

v14 explicitly enables key_pool: reserves, rather than changing the default authentication-only behavior. The verified available keys have independent 15-second request pacing. A limited bucket is cooled for its full reported Retry-After; authentication-rejected buckets are retired. Local usage caps each bucket at 180,000 reported tokens to leave headroom under the observed allowance. If all buckets are unavailable or cannot become ready within the bounded request wait, the client stops safely. Quotas are never changed, and a cooling bucket is not retried early. Keys and raw organization identifiers are not logged. The independent GPT-OSS judge uses a separately available supplied key.

The v14 run completed all 159 recorded queries and native judging, but its pool guard stopped provider access in 31/54 golden samples. Development completion was 96.19%; aggregate golden truth was 64.81% and judge pass was 50.00%. This is an infrastructure-contaminated held-out result, not a production-quality claim. The original artifacts remain unchanged; reports/v14/infrastructure_audit.json records the limitation. The corrected harness records provider outages as hard failures even for expected abstentions, and promotion checks accounting and availability across both phases. A fresh configuration/run is required after quota is available; failed samples must not be selectively replaced.

## Native protocol boundary

The 20B development replays in `reports/provider_20b_development_diagnostic.json` reproduce HTTP 400 `tool_use_failed` for `json<|channel|>commentary`. The opt-in `application_tool_validation` mode asks the official Groq API to return tool calls without server name validation. The adapter strips only the exact observed `<|channel|>commentary` suffix when the remaining name is already advertised. Unknown names and other suffixes are left unchanged for application rejection. Original and canonical names are recorded with the full actual provider usage. Argument, status, retrieved-quotation and failed-retrieval validation remain unchanged. No rejected HTTP generation is assigned guessed usage.

Groq documents this request option in its [API reference](https://console.groq.com/docs/api-reference). This changes the protocol-validation boundary, not the quality gate. It is scoped to the official Groq GPT-OSS endpoint and disabled in historical configurations.
